# Independent forward-use review

Scope: 29 raw requests from `verification/forward-requests.json`, processed using the packaged SKILL.md and task-relevant packaged references. No golden/adversarial scenario documents, prior reports, builder rationale, network access, model invocation, runtime discovery, submission or media acceptance were used. The responses are actual authored scene treatments and decisions in `forward-responses.json`, not a file-presence score. Each request was treated independently; this is one reviewer in one context, not 29 fresh model contexts.

The skill was usable for creating concrete causal coverage. Examples include G-003's explicit throw/flight/pickup/return/handoff, G-006's overlap of recipient grasp with donor release, G-008's preservation of the requested ignition-before-close ordering, G-009's connected-road requirement, and G-011's key ownership chain. The adversarial responses preserve alternatives and name evidence needed rather than merely refusing. ADV-001 correctly allows one image to depict two entities if separately mapped; ADV-002 uses narrower wardrobe scope rather than automatically blocking every conflicting color. Both decisions still depend on inspecting actual references, which were not provided.

## Observed usability defects

1. **Incomplete executable authoring contract for optional supplied structures.** `references/core-contracts.md` names `assembly_plan` and `generation_strategy`, but does not give their required inner keys. The only complete treatment example lets prepare derive both. For authored G-004, the reasonable `assembly_plan.shot_order` key caused `prepare` to fail with `{"status":"BLOCKED","error":"'shot_ids'"}`. The tool did not identify the missing field's owner or point to a usable schema. Reading the implementation revealed `shot_ids` and `reanchor_every_shots`; correcting these made progress. Evidence: the nested `initial_failed_attempt` records in `forward-plan-example.json`. Suggested repair: document a complete authored multi-shot assembly/reset example and validate field shape before indexing it. This is an authoring/documentation usability defect, not an execution security claim.

2. **Acceptance-ID discovery is delayed.** The core authoring contract lists `acceptance_ids` without explaining there that these must be the predefined QG identifiers. The initial authored G-004 used descriptive IDs such as `qa_identity`; validation correctly rejected them with `ACCEPTANCE_CONTRACT`. Reading `references/evaluation-and-repair.md` supplied the valid IDs. Suggested repair: link the gate table beside the ShotSpec field definition or give one dialogue example with applicable gate IDs. Rejection itself is correct. The current top-level routing only directs readers to evaluation for review/regeneration/assembly, making this requirement easy to miss during initial authoring.

3. **`prepare --output` gives no immediate issue details on structural failure.** The intermediate G-004 prepare wrote a failed plan and exited 2 with empty stdout/stderr. A separate validate command produced actionable diagnostics. The documented command sequence eventually works, but an operator inspecting just the prepare result has to discover this behavior. Suggested repair: emit a compact diagnostic or explicitly tell the operator where to run/read validation. Evidence retained with actual exit codes and output.

## Actual authored CLI exercise

`forward-plan-example.json` retains the authored four-shot G-004 treatment, resulting ScenePlan, compiled prompt artifact, exact command arguments/results, and failed attempts. After correcting inner keys and canonical acceptance IDs, prepare, validate and compile each exited 0. Validate reported `PASS` with scope `STRUCTURAL_PLAN_ONLY`, four ordered shots, correct emotional transitions and unchanged screen positions. I also caught and repaired my own missing gaze transition: prose implied partner eyelines while the initial ledger retained train gaze. The final authored state explicitly turns both subjects toward each other. This illustrates why mechanical success alone is insufficient.

The treatment names pending audio and sync stages and requires `visible_speech_sync`; it has no selected/verified profile or actual audio files. Compile success therefore proves only structural prompt production. It does not prove usable lip-sync, good acting, identity retention, current model support, or production readiness. Those are NOT_RUN. Capability negotiation was not attempted because no runtime evidence was permitted or available.

## Remaining weaknesses in the authored responses

G-011's original S7 packs two entries, closing, belts and ignition into eight seconds and explicitly calls for animatic timing repair. It is a useful proposal, but should not be considered compile-ready without redistributing time or adding finer shots. G-012 names a drone-control ownership gap and a stretcher-introduction prerequisite; the proposed coverage must actually insert the landing/retrieval and prop introduction before its hand occupancy and lift can be accepted. Calling these overall drafts `SUPPORTED_PLAN` is too generous if read as fully coherent finalized plans; their stated gaps must remain visible and finalization must be withheld. These are observed forward-response failures under the skill, not claims that a keyword comparison passed all scenarios.

Only G-001 includes a complete compact natural-language generation prompt. Other complex cases supply concrete directing treatments and gaps, which suit plan-only intake, but they are not complete model-specific production packages. No model was selected. Long-form cases have prose timelines/graphs rather than executable serialized artifacts; only G-004 was exercised through the executable contract.

Verdict: useful for substantive planning with explicit capability and evidence boundaries; executable authoring needs better schema discoverability and early diagnostics. This forward use supports neither a 29/29 semantic PASS nor a production/media-quality claim.
